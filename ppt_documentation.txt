SLIDE 2: PROBLEM STATEMENT & CORE OBJECTIVE
--------------------------------------------------------------------------------
• The Problem:
  - Over 90% of cyberattacks start with a malicious or phishing email.
  - Attackers easily fake sender names, hide malicious links behind shorteners, and spoof company brands.
  - Security analysts waste hours manually reading messy email headers, tracing IP hops, and verifying DNS records.

• Our Solution:
  - An intelligent, automated web platform where users upload a raw `.eml` email file.
  - The system dissects the email in seconds: headers, server relay hops, domains, links, geographical routes, and threat database hits.
  - Combines deterministic forensic rules with threat intelligence feeds and AI classification.

--------------------------------------------------------------------------------
SLIDE 3: SYSTEM ARCHITECTURE & DATA FLOW
--------------------------------------------------------------------------------
• High-Level Architecture (3-Tier System):
  1. Frontend (User Interface):
     - Interactive dashboard built with Next.js & Tailwind CSS.
     - Real-time forensic breakdown, security alert badges, and interactive route map.
  2. Backend (API & Forensic Engines):
     - Node.js & Express API written in TypeScript.
     - Modular analysis engines for headers, domains, URLs, routes, geolocation, and threat feeds.
  3. Database & Threat Intelligence:
     - PostgreSQL database managed with Prisma ORM for storing emails and forensic logs.
     - Live external Threat Intelligence APIs (e.g., AbuseIPDB, IP geolocation services).

• Data Flow in Simple Words:
  [User Uploads .eml] ➔ [Express API Parses Email] ➔ [Parallel Forensic Engines Analyze]
  ➔ [Threat Feeds Check Reputation] ➔ [Save to PostgreSQL] ➔ [Render Live Dashboard & Interactive Map]

SLIDE 6: PHASE 2 — EMAIL UPLOAD & MIME PARSING
--------------------------------------------------------------------------------
• Status: Completed
• Plan / Objective:
  - Allow users to drag and drop raw `.eml` files, extract all contents, and save structured metadata.
• What Was Done:
  - Implemented file upload with secure memory handling (5MB limit via `multer`).
  - Extracted email body (plain text & HTML), subject, sender, recipients, timestamps, attachments, and full raw headers.
• How It Is Done:
  - Used `mailparser` (`simpleParser`) library in Node.js to deconstruct complex MIME text into structured JavaScript objects and store them in PostgreSQL.
• Libraries Used:
  - `mailparser`, `multer`.
• Why It Matters:
  - Raw emails are complex encoded text blocks. Parsing turns messy data into clean, queryable fields for inspection.

--------------------------------------------------------------------------------
SLIDE 7: PHASE 3 — EMAIL HEADER FORENSICS & ANOMALY DETECTION
--------------------------------------------------------------------------------
• Status: Completed
• Plan / Objective:
  - Detect common email header forgery techniques used by scammers.
• What Was Done:
  - Automated detection of:
    1. Reply-To Mismatches (display says `company.com`, but replies go to `attacker@gmail.com`).
    2. Return-Path Mismatches (bounced emails route to an unrelated address).
    3. Missing Message-ID (spammers often forget to add legitimate mail server IDs).
• How It Is Done:
  - Regex pattern matching and domain comparison logic inside `analysis.service.ts`.
• Why It Matters:
  - Catches the vast majority of basic phishing campaigns where the attacker tries to intercept victim replies.

--------------------------------------------------------------------------------
SLIDE 8: PHASE 4 — SPF, DKIM & DMARC PROTOCOL AUDIT
--------------------------------------------------------------------------------
• Status: Completed
• Plan / Objective:
  - Verify standard email authentication protocols to check if the sender is genuine.
• What Was Done:
  - Extracted and audited `Authentication-Results` headers for:
    - SPF (Sender Policy Framework): Checks if the sending server IP is authorized by the domain owner.
    - DKIM (DomainKeys Identified Mail): Cryptographic digital signature confirming the email was not modified in transit.
    - DMARC: Checks if the `From` domain matches SPF and DKIM pass status.
  - Added color-coded status badges (PASS / FAIL / NONE) on the frontend dashboard.
• How It Is Done:
  - Regex extraction and validation logic in `analysis.service.ts` and Prisma schema storage.
• Why It Matters:
  - DMARC failures immediately flag domain spoofing and impersonation attacks.

--------------------------------------------------------------------------------
SLIDE 9: PHASE 5 — SENDER & BRAND IMPERSONATION ANALYSIS
--------------------------------------------------------------------------------
• Status: Completed
• Plan / Objective:
  - Catch visual deception tricks such as typosquatting and lookalike domains (e.g., `paypa1.com`).
• What Was Done:
  - Created `domain.service.ts` to detect:
    - Lookalike domains using the Levenshtein Distance algorithm (e.g., swapping `l` with `1`, `o` with `0`).
    - Suspicious keyword stacking (e.g., `apple-security-verify-login.com`).
    - Freemail impersonation (e.g., Sender display name is "Microsoft Support", but email is `@gmail.com`).
• How It Is Done:
  - Custom Levenshtein distance string comparison and target brand keyword matching against a curated brand database.
• Why It Matters:
  - Attackers register fake lookalike domains that pass technical SPF checks; this engine spots the human deception trick.

--------------------------------------------------------------------------------
SLIDE 10: PHASE 6 — URL EXTRACTION & HYPERLINK RISK ENGINE
--------------------------------------------------------------------------------
• Status: Completed
• Plan / Objective:
  - Extract every embedded hyperlink from text and HTML body and assess safety.
• What Was Done:
  - Created `url.service.ts` to pull out all links and scan for red flags:
    - Raw IP addresses used in URLs instead of domain names (e.g., `http://192.168.1.1/login`).
    - Known URL shorteners used to conceal destination (e.g., `bit.ly`, `tinyurl.com`).
    - Unencrypted HTTP links requesting login/banking credentials.
    - Suspicious path keywords (e.g., `verify-account`, `update-billing`).
• How It Is Done:
  - Fast regular expressions and URL parser utilities in Node.js.
• Why It Matters:
  - Malicious links are the primary delivery vehicle for credential harvesting and malware.

--------------------------------------------------------------------------------
SLIDE 11: PHASE 7 — IP & SMTP ROUTE ANALYSIS (RECEIVED CHAIN)
--------------------------------------------------------------------------------
• Status: Completed
• Plan / Objective:
  - Reconstruct the step-by-step physical server route the email traveled across the internet.
• What Was Done:
  - Created `route.service.ts` to parse `Received:` headers from bottom-to-top (Originating server ➔ Intermediate relays ➔ Destination MX).
  - Extracted relay IP addresses, hostnames, transfer protocols, and calculated delay latency between hops.
  - Identified the true Public Originating IP address.
• How It Is Done:
  - Reverse chronological parsing of multi-line `Received` header blocks.
• Why It Matters:
  - Attackers can fake display names, but cannot rewrite intermediate server logs; this reveals the true physical origin server.

--------------------------------------------------------------------------------
SLIDE 12: PHASE 8 — IP GEOLOCATION & INTERACTIVE MAP VISUALIZATION
--------------------------------------------------------------------------------
• Status: Completed
• Plan / Objective:
  - Map the geographic journey of the email visually for analysts.
• What Was Done:
  - Built `geo.service.ts` to convert public IPs into geographic coordinates (Country, City, ISP, ASN, Latitude/Longitude) with offline caching.
  - Created `GeoRouteMap.tsx`: An interactive dark-mode Leaflet map rendering hop markers, popups, and route lines spanning continents.
• Libraries Used:
  - `leaflet`, `@types/leaflet`, Next.js dynamic client-side rendering.
• Why It Matters:
  - Instantly exposes "impossible travel" or foreign server relays (e.g., internal company email originating from an offshore rogue server).

--------------------------------------------------------------------------------
SLIDE 13: PHASE 9 & INTERLUDE — CYBER THREAT INTELLIGENCE (CTI) & LIVE APIS
--------------------------------------------------------------------------------
• Status: Completed
• Plan / Objective:
  - Cross-reference discovered IPs, domains, and URLs against global threat databases in real time.
• What Was Done:
  - Integrated live **AbuseIPDB API** via secure environment variables to retrieve live abuse confidence scores and threat categories.

• Libraries Used:

• Why It Matters:
  - Raw IPs are meaningless without context; Threat Intelligence immediately flags known hacker infrastructure and Tor exit nodes.
